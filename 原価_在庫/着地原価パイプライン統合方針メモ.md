# 着地原価パイプライン統合方針メモ

作成日: 2026-07-07

## 結論

着地原価計算・請求書管理は、CENTRAL本体へ直接混ぜ込まず、専用Webアプリとして構築する。
CENTRALからは専用Webアプリへ遷移できる導線を置き、確定した結果だけをCENTRALへ同期する。

この方針により、ラクマートExcel、関税請求書、請求書台帳、Drive整理、Gemini読取、支払監視を
「経理・原価ツール」の責務として閉じ込めつつ、CENTRAL側の売上・粗利・発注履歴には必要な結果だけを反映できる。

## 採用する構成

### 専用Webアプリ

主役の画面。スマホ/PCブラウザから使う。

- ラクマートExcelをアップロードする
- 請求書PDF/JPG/PNGをアップロードする
- 請求書をGeminiで読み取り、台帳へ登録する
- Mihiroが確認済みチェックを入れる
- 確認済み請求書をリネームして年月フォルダへ整理する
- Excelを処理し、商品別の着地原価を計算する
- CENTRALの `reorder_history` と `product_lifecycle.current_landed_cost` へ同期する

### CENTRAL

業務本体。原価計算そのものは持たず、同期済みの結果を使う。

- `reorder_history` から売上タブの粗利計算に使う着地原価を逆引きする
- `product_lifecycle.current_landed_cost` を商品詳細・ドリルダウン表示に使う
- 発注管理や秘書カードから専用Webアプリへ移動できるリンクを表示する

## CENTRALに置く導線

発注管理タブの上部、レポート同期導線の近くに「着地原価ツールを開く」リンクを置く。
発注判断や在庫補充の流れから、そのまま原価計算へ移動できる位置にする。

将来的には、秘書カードの在庫アラート本文または次アクションからも専用Webアプリへ遷移できるようにする。

専用WebアプリURLはスクリプトプロパティで管理する。
ハードコードはしない。

候補プロパティ:

- `LANDED_COST_WEBAPP_URL`

CENTRAL側はこのURLを読むだけにする。

## 同期境界

専用WebアプリからCENTRALへ書き込む対象は最小限にする。

### 書き込み対象

- `reorder_history`
  - `id`
  - `product_id`
  - `sku`
  - `order_date`
  - `quantity`
  - `unit_price_1688`
  - `landed_cost_actual`
  - `notes`
  - `created_at`

- `product_lifecycle`
  - `current_landed_cost`
  - `updated_at`

### 読み取り対象

- `sku_master`
  - FNSKU、SKU、ASIN解決に使う

- `product_lifecycle`
  - ASINから `id` を解決する
  - 読む列は `id` と `asin` など必要列だけにする

## CENTRALへ持ち込まないもの

以下は専用Webアプリ側の責務にする。

- Excel入庫フォルダ
- 請求書インボックス
- 請求書アーカイブ
- `import_invoices`
- `invoice_ledger`
- `商品別`
- `処理済み`
- Geminiによる請求書抽出
- 支払期限メール
- Driveファイル整理

CENTRALにこれらを混ぜると、商品管理・売上集計・秘書機能の本体が重くなるため避ける。

## 既存データから確認できたこと

旧ツールの計算ロジックは、次の式で成立している。

```text
総仕入額 =
  合計商品代金円
  + 国際運賃円
  + 代行手数料円
  + 関税請求書合計額
  + 国内運賃元 * レート
  + オプション費用元 * レート
```

各商品には、`単価（元） * レート * 出荷数` を基準に総仕入額を案分する。

検証済みファイル:

- `P2026060111490338-302343.xlsx`
  - RW番号: `RW6000052304`
  - レート: `24.55`
  - 関税: `16,300`
  - 総仕入額: `151,963`
  - 旧ツール出力の仕入合計と一致

- `P2026060917233625-302343.xlsx`
  - RW番号: `RW6000052781`
  - レート: `24.6`
  - 関税: `31,300`
  - 総仕入額: `251,004`
  - 旧ツール出力の仕入合計との差は `-2円`
  - 各行丸めの累積差として許容範囲

注意点:

- RW番号のセル位置は固定ではない
- `H15/H16` 固定ではなく、「追跡番号」セルを探して直下を読む

## 実装方針

### アプリの置き場所

専用Webアプリは新規GASプロジェクトとして作る。
リポジトリもCENTRAL本体から分ける。

- GitHub: `https://github.com/koji330-coder/HAKSAI-Landed-Cost`

プロジェクト関連ファイルや管理用Driveフォルダは、Mihiroが作成済みの空フォルダを使う。

- DriveフォルダID: `1m_0CzRoXee5B_8OR-mRqQ_MqyuiLzS60`

このフォルダ自体はプロジェクト・資料・投入導線の起点として扱い、実際のExcel入庫、請求書インボックス、
アーカイブなどのサブフォルダは `setupAll` で冪等に作成する。

### Phase 0: 基盤

- 専用Webアプリ側にシートとDriveフォルダを作る `setupAll` を用意する
- 既存データは消さない
- フォルダID・CENTRAL ID・WebアプリURLはスクリプトプロパティで管理する

### Phase D-1: アップロードだけ先に作る

- Excelと請求書をWebアプリから投入できるようにする
- 拡張子で保存先を振り分ける
- 同一ファイルの二度投げをスキップする

### Phase A: Excel計算

- 旧 `processImportCost` をcore化する
- `Browser.inputBox` はcore内で使わない
- 請求書金額が無ければ `NEED_INPUT` を返す
- 旧ツールと総仕入額が一致することを先に確認する
- 到着日の初期値は、請求書の発行日または請求書日付と同じ日にする
- 到着日は `import_invoices.fba_arrival_date` として保存し、後から手入力で修正できるようにする

### Phase B: 請求書台帳

- Geminiで請求書を読み取る
- `confirmed=FALSE` で保存する
- Mihiroが確認済みにするまで、整理・関税ブリッジには流さない

### Phase A-2: CENTRAL同期

- 最初はdry-runで結果だけ出す
- `product_id` 解決率、`order_date`、金額を確認してから本書き込みする
- `reorder_history.notes` に `依頼書:{p_no}` を入れ、二重同期を防ぐ
- 過去データもこのツールで計算・同期できるようにする
- ただし過去の手入力済み `reorder_history` と二重計上しないよう、dry-runで重複候補を必ず表示する

### Phase C: 支払監視

- `invoice_ledger` の未払・期限超過・期限間近を毎朝確認する
- 該当がある場合だけメールする

### Phase D-2: 操作パネル完成

- Webアプリ上で「投入 → 取込 → 確認 → 整理 → 計算 → CENTRAL同期」まで完結させる
- CENTRALからはこのWebアプリへリンクする

## 開発時の禁止事項

- CENTRAL本体に請求書台帳やDrive整理責務を混ぜない
- `reorder_history` への列位置決め打ち書き込みをしない
- `product_lifecycle` の行全体を書き換えない
- core関数から `Browser.inputBox` / `SpreadsheetApp.getUi()` を呼ばない
- ID、APIキー、フォルダID、WebアプリURLをハードコードしない

## 未決事項

現時点の主要な方針未決は解消済み。

決定事項:

- 専用Webアプリは新規GASプロジェクトにする
- CENTRAL側リンクは発注管理タブ上部、レポート同期導線の近くに置く
- 過去データもこのツールで計算対象にする
- 到着日の初期値は請求書の日付と同じにする
- 到着日は後から手入力で修正できるようにする

実装前に詳細を決める事項:

- 過去データ同期時の重複判定ルール
- 請求書に複数の日付がある場合、初期到着日に採用する日付の優先順位
