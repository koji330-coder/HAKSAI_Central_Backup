# 平均原価の原価不足を埋める手順

目的: 平均原価方式で粗利が未計算・低く見えている商品に、必要な原価ロットを補完する。

平均原価では、着地原価だけでなく `数量` と `適用日` が必要です。  
古い `uncalculated` / `missing_skus` シートは単価中心の補完なので、平均原価用には `moving_avg_cost_issues` を使います。

## 使うシートと関数

出力シート:

- `moving_avg_cost_issues`

主な関数:

- `exportMovingAverageCostIssues()`
- `importMovingAverageCostIssues()`
- `applyMovingAverageCostIssues()`
- `recalcSalesActualMovingAverage(false, false)`

メニューから使う場合:

- `🔧 HAKSAIメンテ` → `② 粗利計算` → `平均原価の原価不足を抽出`
- `🔧 HAKSAIメンテ` → `② 粗利計算` → `平均原価の原価入力を確認（dryRun）`
- `🔧 HAKSAIメンテ` → `② 粗利計算` → `平均原価の原価入力を反映`

## 基本の流れ

1. スプレッドシートを開き直す
2. `平均原価の原価不足を抽出` を実行する
3. `moving_avg_cost_issues` シートを確認する
4. 必要な行に手入力する
5. `平均原価の原価入力を確認（dryRun）` を実行する
6. `moving_avg_cost_issues_import_log` を確認する
7. 問題なければ `平均原価の原価入力を反映` を実行する
8. 過去月も直したい場合は `recalcSalesActualMovingAverage(false, false)` を実行する

## 手入力する列

最低限入力する列:

| 列名 | 内容 |
|---|---|
| `着地原価（手入力）` | 1個あたりの着地原価。例: `152` |
| `初期ロット数量（手入力）` | その原価で在庫に入った数量。例: `300` |
| `適用開始日（手入力）` | その在庫ロットを入れた日。例: `2026-05-01` |

任意入力:

| 列名 | 内容 |
|---|---|
| `処理方針` | `skip` / `スキップ` / `除外` と入れると取り込み対象外 |
| `メモ` | 判断メモ。取り込み処理には使わない |

## 数量の考え方

平均原価は「いつ、何個、いくらで仕入れたか」を使います。  
そのため `初期ロット数量（手入力）` が空だと、`reorder_history` に書き戻せません。

迷ったときの考え方:

- 実際の仕入数量が分かるなら、その数量を入れる
- 実際の仕入数量が不明なら、その期間の販売数を十分カバーする数量を入れる
- 後で正しいロット履歴が分かったら、手入力ロットを見直す

`推奨最小数量` は、その行の販売をカバーするための目安です。  
ただし会計上・管理上の正解ではないので、実際の仕入状況が分かる場合は実数を優先してください。

## 適用開始日の考え方

`適用開始日（手入力）` は、平均原価の時系列に効きます。

- その日以降の売上に対して、そのロットが在庫として使われる
- 売上日より後の日付にすると、その売上には効かない
- 過去月を直したい場合は、対象月の売上日より前の日付にする

例:

- 2026-05 の売上を直したい → `2026-05-01` 以前が無難
- 実際の入庫日が分かる → 実際の入庫日を入れる

## dryRun の見方

`平均原価の原価入力を確認（dryRun）` を実行すると、`reorder_history` にはまだ書き込みません。  
代わりに `moving_avg_cost_issues_import_log` が作られます。

見る列:

| 列名 | 内容 |
|---|---|
| `action` | `dryRun` なら登録予定、`skip` ならスキップ |
| `quantity` | 登録予定の数量 |
| `landed_cost_actual` | 登録予定の着地原価 |
| `order_date` | 登録予定の日付 |
| `message` | スキップ理由 |

よくあるスキップ理由:

| message | 意味 |
|---|---|
| `manual cost/quantity/date missing` | 原価・数量・日付のどれかが空 |
| `same lot already exists` | 同じ SKU/product_id・日付・数量・原価のロットが既にある |
| `policy skip` | `処理方針` に skip 系の値が入っている |
| `SKU/product_id missing` | SKU と product_id が両方空 |

## 反映時に起きること

`平均原価の原価入力を反映` を実行すると、入力済みの行が `reorder_history` に追記されます。

書き込まれる主な列:

- `id`
- `product_id`
- `sku`
- `order_date`
- `quantity`
- `landed_cost_actual`
- `notes`
- `created_at`

反映前に `reorder_history_backup_yyyyMMdd_HHmmss` が作られます。

## sales_actual への反映

`reorder_history` に書き戻しただけでは、過去の `product_lifecycle.sales_actual` は自動では直りません。

日々の売上CSV取込をすると、そのCSVの対象月だけ `sales_actual` が再計算されます。  
過去月もまとめて直したい場合は、原価入力を反映したあとに以下を実行します。

```js
recalcSalesActualMovingAverage(false, false)
```

この再計算で更新される主な項目:

- `landed_cost_used`
- `cost_covered_qty`
- `gross_profit`
- `gross_profit_per_unit`
- `cost_estimated`

売上金額・手数料・販売数などの実績値は、基本的に触らない想定です。

## 作業後の確認

確認するもの:

1. `moving_avg_cost_issues_import_log`
2. `reorder_history`
3. `sales_actual_mavg_recalc_log`
4. Webアプリの売上タブ・発注管理モーダル

期待する状態:

- 原価不足の商品で `landed_cost_used` が入る
- `gross_profit` / `gross_profit_per_unit` が null から数値になる
- `cost_estimated` が必要以上に true になっていない
- 原価未設定の商品が 0 円原価として粗利満額計上されていない

## 注意

- `quantity` を大きく入れすぎると、その原価が長く効き続けます。
- `order_date` を売上日より後にすると、その売上には原価が乗りません。
- 同じロットを何度も登録すると平均原価が歪むため、同一キーの重複はスキップします。
- 原価が不明な商品を 0 円で登録しないでください。未計算のまま残す方が安全です。

## 明日の作業メモ

まずは売上影響が大きい商品から埋めるのがおすすめです。

優先順位:

1. `手取合計` が大きい
2. `status` が `uncosted`
3. `cause` が `no_current_landed_cost_and_no_reorder_history`
4. 実際の仕入数量・着地原価が分かる

入力が終わったら、必ず dryRun を挟んでから反映してください。
