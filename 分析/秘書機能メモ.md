# HAKSAI Central 秘書機能メモ

作成日: 2026-07-07  
最終更新: 2026-07-17

## 目的

秘書機能は、HAKSAI Central内の在庫・広告・ページ・リサーチ情報から「今見るべき次の一手」をカード化する。

単なる通知ではなく、将来的には秘書自身の提案精度も振り返り、却下理由・実行ログ・取りこぼしをもとに自己改善カードを出せるようにする。

2026-07-17以降は、これに商品グロースカルテの改善履歴を接続する。マイカの役割は「異常を知らせる」だけでなく、ガッキーが何を考え、何を実施し、結果をどう評価したかを忘れず、次の判断へ返すことまで含む。

目指す循環:

> 観測 → 提案・相談 → オーナー判断 → 実施記録 → 評価 → 学習 → 次の一手

関連文書:

- React側 `docs/PRODUCT_GROWTH_VISION.md`
  - 商品単位の分析、改善履歴、マイカ相談、長期構想の正本
- 本書
  - 朝礼・スマホ秘書・商品カルテを横断したマイカ全体の運用と接続方針

## 現在の主な構成

対象ファイル:

- `分析/秘書.js`
- `分析/秘書カード詳細.js`

主な実行関数:

- `runDailyBrief(opts)`
  - ルールでイベントを検出する
  - 抑止・重複・優先度で候補を絞る
  - Geminiでカード文面に整形する
  - `action_cards` に追記する
  - `sec_run_log` に実行ログを追記する

主な保存先:

- `action_cards`
  - メインスプレッドシート
  - 秘書カード本体
- `secretary_settings`
  - メインスプレッドシート
  - 秘書の名前、口調、カード上限など
- `sec_run_log`
  - レポート側スプレッドシート
  - `runDailyBrief` の実行履歴

## 現在検出しているイベント

### 在庫

- `stockout_risk`
  - FBA在庫が標準リードタイム内に切れそうで、入庫予定がない
  - 自宅在庫がない場合は海外発注確認へ誘導する

- `home_replenishment`
  - FBA在庫が切れそうだが、自宅在庫がある
  - 海外発注ではなく自宅在庫からFBA補充へ誘導する

### 広告

- `acos_over_breakeven`
  - 直近14日の広告ACoSが損益分岐ACoSを超えている

### ページ

- `cvr_drop`
  - 前期間と比べてCVRが大きく落ちている

### リサーチ

2026-07-18時点で、リサーチ候補は `product_lifecycle` と `page_projects` を正本とする構成へ統一した。旧 `keepa_research_candidates.status=GO` は秘書の参照元から外し、旧Keepa自動リサーチのアーカイブへ分離する。

優先順位:

1. `atlas_page_project_followup`
   - `page_projects` のATLAS由来案件
   - ページ制作や仕入探索まで進んでいて情報量が多い
   - 優先度 `P2`

2. `atlas_sourcing_decision`
   - `product_lifecycle.source = ATLAS_SOURCING_DECISION`
   - ATLAS参入判断済み候補
   - 優先度 `P2`

3. `atlas_manual_research`
   - `product_lifecycle.source = ATLAS_ASIN_RESEARCH`
   - 人間が手動ASINからATLASで取得した候補
   - 優先度 `P3`

## リサーチ参照元を変更した理由

旧 `keepa_research_candidates.status=GO` は一次選別の候補であり、件数が増えると秘書カードが候補の洪水になりやすい。

ATLAS連携後は、次のデータのほうが秘書が提案する価値が高い。

- 人間が手動でASINを送ったカード
- ATLASが参入判断として送ったカード
- ページ制作まで進んだ案件
- ラクマート検索・仕入候補比較まで進んだ案件

そのため、旧GO候補を秘書へ混ぜる互換処理は廃止した。旧候補データそのものは削除せず、別スプレッドシートへ保存する。

## 実行ログ

`sec_run_log` は将来の自己改善レビューの前提データ。

保存先はレポート側スプレッドシート。
追記型ログをメイン側へ置くと、将来doGetや通常操作に影響しやすいため。

列:

- `run_at`
- `run_kind`
- `detected`
- `eligible`
- `generated`
- `mode`
- `dropped_keys_json`
- `detected_by_type_json`
- `duration_ms`
- `error`

見るべきサイン:

- `eligible > generated`
  - Geminiがevent_keyを返さず、候補がカード化されていない
- `mode = fallback`
  - Gemini失敗。API設定、モデル、プロンプト量を確認
- `duration_ms` 増加
  - 参照シート肥大、検出ロジック増加、Gemini応答遅延の兆候
- `detected_by_type_json`
  - イベント種別の偏りを確認する

## 改修時の原則

- UI変更が不要な改善は、まず `runDailyBrief` とログで観測できる形にする
- `action_cards` のスキーマは簡単に変えない
- 追記型・履歴型のシートは原則レポート側へ置く
- `runDailyBrief` の戻り値は既存利用があるため不用意に変えない
- ログ追記はカード生成を止めてはいけない
- Geminiに渡す事実は入力イベント内に閉じる。推測や水増しをさせない
- event_keyは抑止・重複管理の軸なので、変更時は既存カードとの関係を確認する

## 従来からの短期バックログ

- `sec_run_log` と `action_cards` の却下理由を突合する
- 週次の `runSelfReview` を作る
- `self_improvement` カードを生成する
- リサーチ系イベントtype別の採用率・却下率を見る
- ページ制作・仕入探索の停滞をより具体的に検出する

## UI表示方針

2026-07-08に、秘書カードの表示を「優先度グループ + カテゴリ順 + カテゴリ色」に寄せた。

背景:

- ATLAS由来のリサーチカードが増え、在庫補充・広告調整・リサーチが同じ見た目で混ざりやすくなった
- 以前のように、まずP1/P2/P3の重要度で整理されて見える状態を保ちたい
- ただしカード生成や抑止ロジックは変えず、まずUIだけで視認性を上げる

現在の表示ルール:

- 優先度順: `P1` → `P2` → `P3`
- 同じ優先度内のカテゴリ順: `在庫` → `広告` → `ページ` → `価格` → `リサーチ` → `その他`
- 左線は従来どおり優先度を示す
- カテゴリはチップ色と薄い背景色で示す

変更対象:

- `_github_HAKSAI-Central/index.html`
- バックエンドの `runDailyBrief`、`secDetectEvents_`、`action_cards` スキーマには触れない

## カード更新処理の注意点

2026-07-08に、`updateSecretaryCard_` のステータス更新をヘッダー名ベースへ修正した。

背景:

- 一部カードで「完了」時に更新できないケースがあった
- 旧実装は `status` / `status_updated_at` / `dismiss_reason` / `snooze_until` が必ず連続列で並ぶ前提で、`status` 列から4列まとめて `setValues` していた
- `action_cards` は後から列追加してきた経緯があるため、既存シートの列順に依存すると壊れやすい

現在の方針:

- `card_id` / `status` / `status_updated_at` / `dismiss_reason` / `snooze_until` は必ずヘッダー名で列位置を解決する
- `card_id` 比較は前後空白を除去する
- ステータス更新は対象列ごとに `setValue` する

残っている課題:

- `done` は現状、カード行を完了扱いにするだけで、カード種類別の業務実行ログにはなっていない
- 発注推奨などは、将来的に発注数・予定日・メモを保存する専用完了アクションが必要

## 商品改善履歴との連携（2026-07-17）

### Phase 1 実装済み

スマホ版の秘書画面が、React版の商品グロースカルテで保存した `product_actions` を読み取るようにした。

表示内容:

- 直近3日間の「最近やったこと」
- 評価日を迎えた「振り返り待ち」
- 直近14日間の「最近振り返った改善」
- 商品名、ASIN、アクション種別、実施内容、結果、添付画像
- 実施件数、画像記録、マイカ提案から採用された件数に基づく称賛

振り返り操作:

- `効果あり`
- `効果なし`
- `まだ分からない`

`まだ分からない` は1〜90日後へ評価日を延期する。更新可能な状態は `実施済み`、`評価待ち`、`効果あり`、`効果なし` に限定し、アーカイブ済みの記録は更新しない。

主な接続点:

- `分析/商品グロースカルテ.js`
  - `product_actions` の横断読込
  - 安全な評価更新
- `分析/秘書.js`
  - `getSecretaryState_()` の `action_history`
  - 最近・評価待ち・評価済みの分類と称賛文生成
- `コア/コード.js`
  - `updateProductActionReview` POSTルート
- `_github_HAKSAI-Central/index.html`
  - スマホ表示、詳細シート、画像拡大、評価操作

### 現在のデータフロー

1. React版の商品カルテで施策・仮説・画像・評価日を `product_actions` へ保存する。
2. スマホ版の起動時に `getSecretaryState` が朝礼カードと改善履歴ダイジェストをまとめて返す。
3. スマホ版は添付画像をDriveのサムネイルとして遅延表示する。画像本体をスプレッドシートへ保存しない。
4. 振り返り結果は `product_actions` の状態、結果、評価日、更新日時だけを書き換える。
5. React版を次に開いたときも同じ記録を参照し、商品カルテの時系列へ反映する。

### 称賛とAI利用の境界

今回の称賛文はGeminiを呼ばず、実施件数、アクション種別、添付画像数、マイカ提案の採用数から決定的に生成する。

理由:

- 起動のたびに費用と待ち時間を発生させない
- 同じ事実から評価がぶれない
- 実際に残した記録だけを根拠に褒める

AIは、複数データを解釈する相談、原因仮説、施策候補、文章化に使う。集計、期限判定、損益分岐、優先順位が数式で決まる部分は原則としてコードで処理する。

## マイカの役割分担

### 1. 朝礼マイカ

- 受け身でも重要事項を取りこぼさないための入口
- 在庫、広告、ページ、リサーチのイベントを優先度順に提示
- 事実中心で、今見るべき項目を絞る

### 2. 商品相談マイカ

- ASIN単位の売上、粗利、広告、流入、在庫、Keepa、改善履歴、画像を読む
- 一般論ではなく「この商品で何が起きているか」を扱う
- 一往復で終わらず、ガッキーの反論・補足・未反映情報を会話文脈へ加える
- 回答から改善アクションの下書きを作る

### 3. 振り返りマイカ

- 評価日を迎えた改善を忘れないように促す
- 前後の数字と当時の仮説を並べる
- 結果の良し悪しだけでなく、何を学べたかを残す
- 実施と記録そのものも、具体的な根拠付きで認める

### 4. 将来の経営秘書マイカ

- 商品横断で成功・失敗パターンを探す
- 在庫、広告、価格、商品ページ、資金繰りの競合する優先順位を調整する
- 提案の期待利益、最大損失、評価期間、撤退条件を示す
- オーナーの承認を得てから実行系APIへつなぐ

## 保存量と長期運用

履歴が増えても、すべてを毎回AIへ渡さない。

- `product_actions` は1施策1行の正本とする
- 画像バイナリはDriveへ保存し、シートにはIDとメタデータだけを置く
- 会話履歴は相談単位で保持し、通常表示は直近または選択した相談だけを読む
- 古い会話は削除せず、相談要約・確定事実・オーナー判断を別の短い記憶へ蒸留する
- AIへ渡す文脈は、対象ASIN、期間、相談テーマに合う記録だけを検索する
- 一覧APIは本文・画像本体を大量返却せず、要約と件数を優先する
- 将来件数が増えたら、年月・ASIN・状態の索引シートまたは外部DBを検討する

スプレッドシートの行数よりも、毎回全件走査する実装と、全履歴を無選別にプロンプトへ入れることのほうが先に問題になる。保存と利用を分離する。

## 将来ロードマップ

### Phase 2: 振り返りを習慣にする

- 評価待ち件数を朝礼の優先カードへ統合
- アクション詳細からReact版の商品カルテへ直接移動
- 実施前後7日・30日、前年同月、曜日差を並べた自動比較
- 売上、販売数、粗利、CVR、ROAS、TACoS、在庫日数から評価指標を選択
- 評価延期の理由と、次に確認する条件を保存
- スマホから振り返り画像・補足メモを追加

### Phase 3: 提案と結果を結ぶ

- マイカの提案IDをアクションへ保存し、提案→採用→実施→結果を追跡
- 却下・修正理由も学習材料として保存
- 「効果あり／なし」だけでなく、期待値との差と副作用を記録
- 広告変更履歴、価格変更、入荷、欠品を自動イベント化
- 検索語・ターゲット別の広告後利益と改善履歴を接続
- 毎週・毎月の振り返りレポートを自動生成

### Phase 4: HAKSAI固有の学習

- 商品群、価格帯、カテゴリ、ライフサイクル別の成功パターン検索
- 画像差し替え、A+、広告拡大、値上げ等の施策別ベースラインを作る
- ガッキーの判断基準、反論、例外条件を短い運用原則へ蒸留
- 過去の類似施策を根拠として、次の提案に引用
- マイカ自身の提案採用率、的中率、利益貢献、過剰警告率を評価
- 無料モデル・高性能モデルを相談の重要度で使い分ける

### Phase 5: API自動化と承認付き実行

- Amazon Ads APIで広告実績と変更履歴を自動取得
- SP-APIで売上、流入、在庫、返品を定期取得
- 予算、入札、価格、発注量の複数シナリオを比較
- 期待利益、資金拘束、欠品リスクを同時に提示
- ガッキーが承認した操作だけを広告・発注・ページ制作へ反映
- 実行後は自動で評価日と監視条件を設定

### Phase 6: 夢物語

- 全商品を巡回し、異変と機会を発見する半自律型の商品経営AI
- 広告、商品ページ、在庫、財務、リサーチの専門AIによる会議
- 各専門AIの提案を、マイカがHAKSAIの制約とガッキーの価値観で統合
- 商品ごとのデジタルツインで、値上げ、広告増額、発注量を事前シミュレーション
- 画像・A+・広告案を生成し、小さく試し、結果から次案を作る継続実験
- 終売商品の失敗も含めた全商品史を、新商品リサーチと商品開発へ還流
- 店舗全体の現金、在庫、利益、成長速度を同時最適化する経営シミュレーター

## 将来も守る原則

- 事実、推定、提案を混ぜない
- マイカはガッキーの意図を尊重するが、必要なら根拠付きで反対する
- 一般論より、対象商品とHAKSAIの実績を優先する
- 未反映の発注など、システム外の事実を会話で訂正できるようにする
- AIの提案を自動で事実扱いしない
- 自動変更は段階的に導入し、当面は必ずオーナー承認を通す
- 記録を増やすこと自体を目的にせず、次の判断に再利用できる形で残す
- 撤退や効果なしも失敗として隠さず、判断精度を上げる資産として扱う
- UI上のマイカらしさと、分析の深さは別に設計する。口調設定で思考を浅くしない

## 既知の制約

- 現在のAI相談品質は利用モデルの推論力に強く依存する
- 発注済みでも発注データへ未反映なら、在庫切れ警告が誤ることがある
- 日次セッション・CVRがない期間は、売上変化を流入と転換へ完全分解できない
- 施策が重なると、単純な前後比較だけでは単独効果を断定できない
- 称賛文は現状ルール生成であり、施策の難易度や努力量までは判断しない
