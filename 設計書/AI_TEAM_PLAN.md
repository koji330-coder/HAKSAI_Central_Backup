## 0. 結論（先に3行）

1. **新しいAIを作る話ではない。** 既にマイカ＋Gemini機能5つ＋Claudeスキル8つが揃っている。
   足りないのは「誰がどこまで決めていいか」と「誰から誰へ何を渡すか」の定義だけ。
2. **チームの実体はエージェントではなく、部門間のハンドオフ契約と権限レベル。** ここを固定すれば、
   中身のモデルが Gemini でも Claude でも入れ替え可能になる。
3. **最大のボトルネックは人間がI/Oバスになっていること。** Amazon実績データがCSV手動取込でしか
   入ってこないため、販売部・供給部は構造上どう組んでも日次自動運転にならない。Phase 0 で決着が要る。

## 1. 設計原則

### 原則1 — 境界は「業務フェーズ」で切る（機能で切らない）
既存スキルは既にフェーズで切れている（参入判断／ページ制作／広告／診断）。エージェントの境界も
これに揃える。「画像担当」「文章担当」のような機能分割で切ると、1商品の情報が複数エージェントに
散って引き継ぎコストが跳ね上がる。

### 原則2 — 記憶はエージェントに持たせない。HAKSAI Central が唯一の正
会話ログやチャット履歴を記憶と見なさない。判断も結果もシートに書く。理由：
- エージェントは常にコールドスタートする前提のほうが壊れにくい
- 人間が後から検算できる
- モデル交換時に記憶が失われない

### 原則3 — 人間の役割を「作業者」から「承認者・所感提供者」へ固定する
オーナーが手を動かすのは**不可逆・金銭・アカウントリスク**の3つだけ。それ以外で人間の手が要るなら、
それは設計の失敗として記録する。

### 原則4 — 監査役に実行権限を与えない
全部門が同じ数値ソース（HAKSAI Central）を信じて動くため、数値が壊れると**全員が同時に間違える**。
これを検出する係は、他部門の成果物に依存しない独立した立場である必要がある。

### 原則5 — 人間の所感 ＞ AIの判定
`FROZEN_教訓還流システム構想.md` §1.3 の原則をチーム全体に拡張する。オーナーの `owner_note` や
却下理由は、どのエージェントのverdictよりも上位に置く。

## 2. 前提となる制約（これを直視しないと机上の空論になる）

| 制約 | 内容 | 影響を受ける部門 |
|---|---|---|
| **SP-API / 広告API 未接続** | 外部APIは Keepa と Gemini のみ。売上・広告・在庫の実績は `広告レポート取込.js` `検索クエリパフォーマンス取込.js` 等の手動CSV取込が入口 | 販売部・供給部（週次までしか回せない） |
| **出品・入札・価格の書き込み手段が無い** | 提案は作れるがセラーセントラルへの反映は全て人手 | 販売部・制作部 |
| **ラクマート/1688は非API** | 仕入先探索は画像・スクショ経由のVLM解析（`page_skill_pack.js`） | 探索部 |
| **GASの実行時間・トリガー上限** | 重い分析を常時走らせられない | 全部門 |

→ **この制約下では「全自動運営」は目標にならない。** 現実的なゴールは
**「オーナーの1日を、承認3件と所感入力に圧縮する」**。プラン全体をこの目標に最適化する。

### 3.0 共有記憶レイヤー — HAKSAI Central

チームの「机」。全エージェントの入力元であり出力先。人格ではないが、組織図上いちばん重要。

| 種別 | シート | 役割 |
|---|---|---|
| 商品の一生 | `product_lifecycle` `sku_master` `page_projects` | 全部門の共通ID空間 |
| 市場 | `keepa_research_candidates` `keepa_seller_master` `listing_snapshots` | 探索部の一次データ |
| 販売実績 | `transaction_history` `ad_performance_history` `business_report_period` | 販売部・監査役 |
| 供給 | `reorder_history` `period_costs` `inventory_snapshot` | 供給部 |
| 学習 | `research_lessons` （将来 `research_principles`） | 司書 |
| 指示・承認 | `action_cards` `sec_run_log` | マイカ |

**ルール**: エージェントは自分の担当シート以外へ**書き込まない**。読むのは自由。
書き込み権の重複がチームの崩壊要因になるため、シート単位でオーナーシップを固定する。

### 3.1 マイカ ／ Chief of Staff（司令塔・秘書）

| 項目 | 内容 |
|---|---|
| **一言で** | オーナーの唯一の窓口。**部門の仕事はしない。** |
| **責務** | ① 朝礼で「今日オーナーが決めること」を3件以内に絞る ② イベント検知 → 担当部門へタスク発注 ③ 承認待ちキューの管理 ④ 却下理由の回収と司書への受け渡し |
| **やらないこと** | 参入判断・広告調整・発注数量の決定。**自分で判断し始めた瞬間に司令塔が崩れる。** |
| **既存資産** | `分析/秘書.js` `分析/秘書カード詳細.js` `action_cards` `secretary_settings` `sec_run_log` |
| **現状との差分** | 今は「検知して知らせる」で止まっている。**「検知 → 担当エージェントへ投げる → 結果を承認待ちに積む」までを担当する**よう役割を拡張する |
| **権限** | L2（タスク割当・カード生成は自動。判断は一切しない） |
| **稼働** | 毎朝＋イベント駆動 |

> 設計上の注意: マイカの人格・トーン（ピンクの朝礼カード）は `DESIGN.md` §2.2/§4.2 のスコープに厳密に留める。
> 他のエージェントに人格を与えない。**人格を持つのはマイカだけ**にして、他は「部署」として扱う。
> 理由：人格が増えるとオーナーが誰に話しかけるべきか迷い、司令塔の一元化が壊れる。

### 3.2 探索部 ／ Scout（リサーチ・参入判断）

| 項目 | 内容 |
|---|---|
| **一言で** | 「どの市場に、後発で、いくらで入るか」を決める素材を作る |

| **稼働** | 週次バッチ＋候補到着イベント |

**内訳（3つの席）**

| 席 | 担当 | 権限 | 備考 |
|---|---|---|---|
| Scout-A 一次選別 | Keepa数値ゲート（月販・競合数・ランク変動・NGカテゴリ） | **L2**（機械的判定なので自動でよい） | 既存の `ステータス自動付与.js` が原型 |

> 設計上の注意: Scout-A を L2 自動にできるのは**判定基準が数値だけで書けるから**。ここに「なんとなく良さそう」を
> 混ぜた瞬間に L1 へ降格させる。自動化の境界＝**基準を数式で書けるかどうか**。

### 3.6 監査役 ／ Auditor（横断・数値健全性）

| 項目 | 内容 |
|---|---|
| **一言で** | 他部門の出力を疑う係。**唯一、成果物を出さない部署。** |
| **責務** | ① 原価未登録・粗利未計算・欠品による実績歪みの検出 ② 各部門の提案が損益分岐を割っていないかの検算 ③ アカウント健全性（規約リスクのある表現・画像）のチェック |

| **稼働** | 月次＋各部門の成果物が承認キューに載った時 |

> **なぜ必要か**: 原則4の通り、全部門が同じ数値を信じるため、数値が壊れると全員が同時に、
> かつ**もっともらしく**間違える。既存コードに「原価未登録抽出」「粗利未計算抽出」が複数あることが、
> この問題が実際に起きている証拠。今はオーナーが手動で叩いている。これを職務にする。

### 3.9 意図的に置かない席

| 席 | 置かない理由 |
|---|---|
| 汎用「なんでも屋」エージェント | 境界が壊れる。困ったらマイカが人間に戻す |
| カスタマー対応（レビュー返信・問い合わせ） | アカウントリスクが高く、AIの誤答コストが売上損より大きい。**ただし現状の負荷が不明なため要確認**（§7 未決事項） |
| 「経営企画」的な上位エージェント | 経営判断はオーナーの仕事。AIに戦略を決めさせると、判断根拠がブラックボックス化して原則5が崩れる |

## 4. 権限モデル（本プランの中核）

**この表が守られている限り、中のモデルは何に入れ替えてもよい。**

| レベル | 意味 | 誰が | 例 |
|---|---|---|---|
| **L0** | 観測・警告のみ。書き込みもしない | 監査役 | 数値矛盾の指摘 |
| **L1** | 下書き・提案の作成（オーナーが採否） | 探索・制作・販売・司書 | 参入判断カルテ、入稿パック、入札変更案 |
| **L2** | 可逆な自動実行（事後報告のみ） | マイカ、Scout-A、データ取込 | Keepa取得、ステータス自動付与、カード生成 |
| **L3** | 人間の明示承認が必須 | 供給部、広報部、全部門の外向き行為 | 発注、価格改定、広告予算増、出品公開、note公開、スキル改訂 |

**判定ルール（覚えるのはこれだけ）**

> **金が動く・外部に出る・取り消せない → L3**
> **基準を数式で書ける・元に戻せる → L2**
> **それ以外は全部 L1**

## 5. ハンドオフ契約（チームの実体）

エージェントを何人置くかより、**この矢印が定義されているか**が成否を決める。
既に `sourcing_decision_pack.js` `page_skill_pack.js` `listing_audit_pack.js` `pack_view.js` という
「パック」の思想が実装されている。**これを全ハンドオフに拡張する**のがチーム化の実務。

| From → To | パック名 | 中身（最低限） |
|---|---|---|
| 探索部 → 制作部 | 参入判断パック | 勝ちパターン区分／ターゲット競合ASIN／価格ポジション／訴求軸／損益分岐価格 |
| 制作部 → 販売部 | 入稿パック | 設計KW／**ターゲットにした競合ASIN一覧**／想定CVR／訴求の優先順位 |
| 販売部 → 制作部 | 改稿指示 | ファネル分解結果／原因区分（露出/価格/ページ/在庫/レビュー）／修正対象モジュール |
| 販売部 → 供給部 | 需要見込み | 広告による需要増分／セール予定 |
| 供給部 → 販売部 | 欠品予測 | 欠品見込日／**欠品前に広告を絞る指示** |
| 全部門 → 司書 | 判断ログ | 何を根拠にどう判断し、結果どうだったか |
| 司書 → 全部門 | 原則層 | `research_principles`（蒸留済み・矛盾解消済み） |
| 監査役 → マイカ | 警告 | 数値の不整合／損益分岐割れの検算結果 |

> **特に重要な1本**: 制作部 → 販売部 の「ターゲットにした競合ASIN一覧」。
> `amazon-ad-plan` の運用哲学（ページ作成時にターゲットとした競合商品の商品ターゲティングから開始）は、
> このハンドオフが機能して初めて成立する。**現状ここが人の記憶に依存している。**

## 7. 導入フェーズ

### Phase 0 — 前提の決着（新規開発なし・意思決定のみ）
1. **人間I/Oバス問題の決着**。次のどちらかを選ぶ:
   - (a) SP-API / Amazon Ads API を接続し、販売部・供給部を日次化する（開発コスト大／効果大）
   - (b) APIは入れず、CSV取込を「週1回15分の定型作業」に固定し、週次運用を正式な設計とする（コスト小）
   - ※ **これを決めないと販売部・供給部の設計が確定しない**
2. **実行基盤の決定**（§8 未決事項1）
3. ハンドオフパックのスキーマ確定（§5 の表を実データ項目まで落とす）

### Phase 1 — 既存の再編成（**新規開発ゼロ**）
- 既存8スキル＋マイカに、**役割名・権限レベル・出力契約**を付与する
- 「AIチーム憲章」を `CLAUDE.md` もしくは本書の確定版として置き、全エージェントの起動時参照にする
- シートごとの書き込みオーナーシップを明文化する
- **効果**: 「どのスキルを呼ぶか」の迷いが消える。承認すべきものと自動でよいものが分離する
- **コスト**: ドキュメント作業のみ

### Phase 2 — 欠員補充（インパクト順）
1. **Supply-Forecast**（発注推奨）— 金額インパクト最大。欠品は学習まで汚染する
2. **Growth-Price**（価格管理）— 判断基準が数式で書け、粗利に直撃する
3. **Auditor**（監査役）— 上2つが動き出す前に置くべき保険

### Phase 3 — 自律化
- L2 の範囲拡大（基準を数式で書けたものから順に昇格）
- マイカのタスク割当自動化
- 司書の起動（`FROZEN_教訓還流システム構想.md` の凍結解除・同書の開始条件に従う）
